- **47 个远程 URL → 46 个本地文件**，19.43 MB，位于 `参考资料/dkucs-blog/assets/`，放在归档目录内部而非仓库根，保持归档自足、可整体搬走。

- **校验方式**：56 处引用（44 正文 + 12 封面）↔ 46 个磁盘文件，双向无失效、无孤立。每张图另做了 magic byte 检查与尺寸解析，确认是有效图像而非错误页。

**踩到的坑（重要，下次直接绕开）**：macOS 的 `file` 命令对 JPEG 只报 **DPI**（如 `density 96x96`）而不是像素尺寸，对 WebP 干脆不报尺寸。用 `file` 统计图片尺寸会得到一列错误数字。正确做法是直接解析文件头：PNG 读 IHDR（偏移 16 起的两个大端 uint32）、JPEG 扫描 SOF 段（0xC0–0xCF 去掉 0xC4/0xC8/0xCC）、WebP 按 RIFF 块遍历（VP8X 取 canvas 尺寸、VP8L 取 14 位打包值、VP8 取帧头）。解析器留在 `/tmp/dims.py`。

**改写真名的正则**：`cover_image: "URL"` 与 `![alt](URL)` 两处分别替换，替换时以 `"` 和 `)` 作边界——镜像站存在 `image1.webp` / `image10.webp` / `image11.webp` 这类前缀相同的文件名，无边界替换会串改。

## 社团官网开发（同日，第二轮）

按天成要求仿照 <https://www.dkucs.com> 做 DKU AI Club 官网，公开页面 + 管理员后台（可改旧事件、建新事件），既有事件内容用 `参考资料/dkucs-blog`。

### 技术选型（已落地）
- **Vite 7 + React 19 + TS + Tailwind 3.4 + shadcn/ui**（模板取自 `modern-web-app` skill，但 init 脚本在 macOS 上因 `sed -i ''` 展开问题中断，改为手工 `cp -R template/. <root>/`）。
- **HashRouter**：部署环境是无 SPA fallback 的静态托管，BrowserRouter 深链会 404。
- **云后端**：`workbuddy_cloud_service` 激活，appId `wbapp_FSdVvw7EfcuaomD8qeHlX4`，endpoint `https://dku-ai-club.app.workbuddy.host`。SDK 用 npm 形式 `@tencent-ai/workbuddy-cloud-sdk@dev`。
- **必须给 SDK 传 `Database` 泛型**：不给泛型时 `createWorkBuddyCloud` 推断出的是 `never` 而不是文档说的 `any`，`insert/upsert` 全部报 TS2345。手写一份 supabase 形状的 `Database` 类型放在 `src/lib/cloud.ts` 即可。

### 数据库结构（云 PostgreSQL）
三张表：`events`（公共只读 + 管理员可写）、`site_settings`（key/value JSONB，公共只读）、`admins`（管理员名单）。
- 关键设计：**不用 SECURITY DEFINER 函数**。管理员判定写成策略里的子查询 `auth.uid() IN (SELECT user_id FROM public.admins)`；`admins` 自身的 SELECT 策略是 `user_id = auth.uid()`，于是非管理员查到的子查询为空、判定自然为假，既不递归也不泄露名单。
- 副作用：`anon` 也必须 `GRANT SELECT ON admins`，否则匿名用户查 `events` 时策略里的子查询会撞权限错误（42501）而不是返回空。
- 首位管理员用策略 `WITH CHECK (user_id = auth.uid() AND NOT EXISTS (SELECT 1 FROM admins))` 自助认领；「是否还有空位」这个 UI 提示存在公共可读的 `site_settings` 的 `meta` 键里（管理员表本身读不到别人的行）。

### 内容分层（重要，是本次绕开成本的关键决策）
12 篇正文合计约 56 KB，全部经工具调用写进数据库代价很高。改成两层合并：
1. `public/content/events.json` —— 随站点打包的内置归档（12 篇全文 + 原名 slug + source_credit/source_url）。
2. 云数据库 `events` —— 管理员新建/编辑过的记录。

公开页 `fetchPublicEvents()` 按 slug 合并，**数据库优先**；`status='archived'` 表示对公开页隐藏。于是「编辑归档事件」= 写入一条同 slug 的库记录覆盖它，「删除库记录」= 归档版本重新出现。任何一条都能被后台完整增删改，且初始内容零成本随包发布。

### 配图
`参考资料/dkucs-blog/assets` 46 张 → `public/images/events/`，用 `sips -s format jpeg -s formatOptions 72 -Z 1600` 压缩（19.43 MB → 13.3 MB，单张最大 452 KB）。**sips 能直接读 webp**，不需要额外工具。命名规则：`images/blog/x` → `x.jpg`，`images/blog/dir/x` → `dir-x.jpg`，`events/x` → `x.jpg`（扁平化会撞名，`poster.webp` 有 5 个同名文件）。

### 踩到的坑
- **并行修改同一个文件会丢写**。同一 message 里发两个 `Edit` 到同一文件，两个都返回成功，实际两个都没落盘（后一次以原始内容为基准覆盖）。同理，并行发多条 `exec_sql` 建策略时也有 4 条静默丢失。**教训：同一目标的写操作必须串行，写完要回读核验。**
- 上传图片走「前端等比压缩成 data URL 存进 `events.cover_image`」，不用云 Storage —— 因为 Storage 的 `shared/` 只对已登录用户可读，匿名访客读不到，公开站点会挂图。
- 账号登录**只在发布域名上可用**（服务端精确匹配 Origin），localhost 预览无法验证登录与写库。

## 内容页（/events/<slug>）统一宽度 + 去装饰（同日，第五轮）

### 宽度不一致是量出来的，不是看出来的
在浏览器里实测（1440 宽视口）:

| 块 | 左边缘 | 宽度 | 来源 |
|---|---|---|---|
| 封面图 | 240 | 960 | `max-w-5xl` |
| 标题/摘要 | 304 | 832 | `max-w-4xl` |
| 正文与正文图 | 368 | 704 | `max-w-3xl` |

## 管理员可以再授权其他邮箱（同日，第四轮）

天成要求：管理员账号要能把管理员权限授予其他邮箱地址的账号，即「管理员可以变成更多管理员」。

### 为什么必须改成按邮箱授权
原设计里 `admins.user_id` 是主键且 `DEFAULT auth.uid()`，一行对应一个**已注册账号**。但被指定的人往往还没有账号 —— 要授权就得先让他注册，而「先注册」这一步没人能替他做，管理员点不了。所以授权入口必须落在**邮箱**上，而不是账号 id 上。

### 结构调整（`admins` 表）
- 主键从 `user_id` 换成新的 `id bigint GENERATED BY DEFAULT AS IDENTITY`；`user_id` 改为**可空**并加唯一约束（Postgres 允许多个 NULL）。
- 新增 `added_by_email`（谁加的）、`display_name` 已有但这次才启用为「显示名」。
- `lower(email)` 上加唯一**部分索引**（`WHERE email IS NOT NULL`），大小写不敏感去重。
- 迁移写成 `DO $$ ... $$` 块 —— 工具单次只允许一条语句，DO 块是「一条语句里塞多条 DDL」的绕法；复杂 SQL 用 `sqlBase64` 传避免转义。
- **坑**：`ALTER COLUMN user_id DROP NOT NULL` 必须排在**摘掉旧主键之后**，否则报 `42P16 column "user_id" is in a primary key`。第一次就是这么失败的（DO 块整体回滚，无副作用）。

### 权限判定：改成 SECURITY DEFINER 函数（**推翻本文件第二轮的「不用 SECURITY DEFINER」结论**）
第二轮刻意避开 SECURITY DEFINER，靠策略内子查询躲递归。这次必须反过来，原因是新需求要「读整份名单」和「按邮箱判权限」，两者都要求策略能访问同表 / 跨表，纯子查询写不出来。

三个函数：
- `is_site_admin()` —— `uid 匹配 user_id` **或** `user_id IS NULL 且 lower(email) 等于 auth.email()`。这是全部策略的统一入口。
- `admin_slot_open()` —— 名单为空时返回 true，用于首位管理员自助认领。
- `bind_admin_invite()` —— 登录后把「仅登记邮箱」的行绑定到本人账号。

**递归为什么不会发生**（已实测，见下）：这三个函数是 `SECURITY DEFINER`，属主 = 表的属主 `cloudbase_postgres_pgdb_rpcn7j6h`；三张表 `relforcerowsecurity` 都是 `false`，属主读自己的表会**绕过 RLS**，所以函数内部的 `SELECT FROM admins` 不再触发策略，链条断掉。

`bind_admin_invite()` 取邮箱的来源是 **`auth.users` 表**（`WHERE sub = auth.uid()`），不是 JWT 里的 email 声明 —— 这是可信来源，客户端伪造不了。JWT 的 `auth.email()` 只作为 `is_site_admin()` 的补充路径，取不到就返回 NULL、自然不匹配，不会误判。

### 前端
- `data.ts` 新增 `fetchTeam()` / `inviteAdmin()` / `renameAdmin()` / `removeAdmin()`，`AdminState` 加 `uid`。
- `readAdminState()` 先调一次 `bind_admin_invite()`（失败静默吞掉）再判定，保证「登记了邮箱但没绑定」的人也能进后台。
- 新页面 `pages/admin/AdminTeam.tsx`，后台第三个页签 Administrators：邮箱 + 可选显示名添加、状态徽章（`Active` / `Awaiting sign-in`）、重命名、移除。
- **`insert()` 不要链 `.select()`**：`admins_read_all` 策略是 `is_site_admin()`，而同一条语句里刚插入的行对 STABLE 函数不可见（同一快照），RETURNING 会拿到空数组、被误判成失败。改成只看 `error` —— `WITH CHECK` 违规一定会抛错，不会静默失败。UPDATE/DELETE 仍可用 `.select()`，因为目标行本来就可见。
- `inviteAdmin` 必须**显式传 `user_id: null`**：该列 `DEFAULT auth.uid()`，不显式置空会把邀请人自己的账号绑上去，等于把权限给了错的人（注意这与文档「不要传 null 触发默认值」的告诫方向相反，此处正是要压制默认值）。

### 验证方式（重要，可复用）
工具跑在表属主角色上、绕过 RLS，所以**常规查询验证不了策略**。可用的办法是在 `DO` 块里 `SET LOCAL ROLE authenticated;` 切换角色，再用 `set_config('request.jwt.claims', '{"sub":"...","email":"...","role":"authenticated"}', true)` 伪造 JWT，最后 `RAISE EXCEPTION` 把结果当错误信息抛出来读。整块回滚，不留痕。

实测结论：
- 匿名 / 普通登录用户：`is_site_admin=false`、看不到名单（0 行）、不能插入名单（`42501`）—— 越权被拦住。
- 被登记邮箱的人：`is_site_admin=true`、能读到名单 —— 授权生效。
- 其它邮箱：`false`。
- 补一条：即使未绑定 `user_id`，靠 `auth.email()` 也能判为管理员 —— 双路径冗余，绑定失败不会导致授权失效。

## 本地测试环境（同日，第十轮）

天成：「我想测试完整功能，你能不能赋予这个网站在本地测试的能力（例如，数据库本地化，本机是有 postgresql 安装的）」。

### 约束（先探明的）
- 本机有 PostgreSQL 18.4（Homebrew）**已在跑**：127.0.0.1:5432；有 `docker` 命令但 **Docker 守护进程没起**；没有 `supabase` CLI。所以他提的「用本机 PostgreSQL」是唯一顺手的路。
- 登录**只在发布域名上可用**（服务端精确匹配 Origin），所以本地必须连账号系统一起替换，不能只换数据库。
- 不能走「代理到线上并伪造 Origin」那条路：那会写到**生产库**、还会真发验证码邮件。

### 做法：本地 API 顶替托管后端
`localdev/` 六个文件 + `src/lib/localClient.ts`，前端页面一行未改。

- `schema.sql`：`public` 三张表 + `auth` schema 的 `uid()`/`email()`（读 `request.jwt.claims`）+ 三个 SECURITY DEFINER 函数 + RLS 策略（**逐条抄自线上 `pg_policies`**），另加 `local_auth`（users/sessions/codes，浏览器可达的角色对它没有任何权限）。
- `server.mjs`：无依赖（只用 `node:http` + `pg`）的 API。`POST /api/db` 把前端的 supabase 形状调用翻成参数化 SQL；`/api/rpc`；`/api/auth/*` 实现注册 / 密码登录 / 验证码 / 重置 / 会话，签发 HS256 JWT。**每笔数据库请求都在事务里 `set_config('request.jwt.claims')` + `set local role anon|authenticated`**，让 RLS 真的生效；UPSERT/UPDATE/DELETE 无 filter 一律拒绝。
- `src/lib/localClient.ts`：只覆盖站点真正用到的那一小片 API（builder 的 from/select/insert/update/upsert/delete/eq/order/limit/maybeSingle/then，加 rpc 与 6 个 auth 方法），返回同样的 `{data, error}` 信封。
- `src/lib/cloud.ts` 用 `import.meta.env.VITE_LOCAL_BACKEND === '1'` 二选一。构建期常量 → 生产包自动摇掉 shim（**实测产物大小与改动前完全一致，566.72 kB**）。

### schema 镜像的四处硬错误（查线上才发现，值得记住）
这次为了对齐类型去查了 `information_schema.columns` / `pg_proc` / `pg_policies`，发现本地镜像之前是「凭印象」写的，有四处会真的出错：

1. **`auth.uid()` 线上返回 `text`**，我写成了 `uuid`。`admins.user_id` 是 `text`，于是每条策略都报 `operator does not exist: text = uuid`。`auth.email()` 同理，且线上会先读 `request.jwt.claim.email`（单数）再退回 `request.jwt.claims`。

3. **`events.tags` 是 `text[]`，不是 jsonb**（jsonb 的只有 `gallery`）。`server.mjs` 的 `toParameter` 原来把 tags 当 jsonb 序列化，会写不进去；改成数组原样交给驱动。
4. **`events.event_date` 是 `date`**。`pg` 默认把 date 解析成本地午夜的 `Date`，序列化成 ISO 再被前端 `slice(0,10)` 会**差一天**（UTC+8 下 `2026-05-05` 变 `2026-05-04`）。修法：`pg.types.setTypeParser(1082, v => v)` 原样返回字符串。

| 表权限 | 管理员可写 | `anon`/`authenticated` 对任何表**只有 SELECT** |
| 删掉的东西 | `admins` 表、`is_site_admin()`、`admin_slot_open()`、`bind_admin_invite()`、`cloud.auth.*`、`local_auth` 全库、`auth.users` | ← 两边数据库都已删除 |

**关键实测结论（决定了整个设计）：匿名角色调用 `SECURITY DEFINER` 函数可以写库。** 因此「没有账号也能改网站」在这套后端上是成立的，不需要任何身份系统。密钥**作为函数命名参数**传入——我先试过自定义请求头，探测发现托管网关只透传它自己的内部头，`request.headers` 拿不到。
